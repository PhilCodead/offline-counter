# Подготовка релиза

Опубликованный релиз связывает версию исходников, APK и сертификат подписи. Файлы существующего релиза не заменяются новой сборкой: исправления выпускаются под новым номером.

## Сборка

Используйте окружение из [руководства разработчика](DEVELOPMENT.md#окружение). Для предыдущего выпуска переключитесь на соответствующий тег и используйте требования из его исходников.

Перед сборкой обновите `versionName`, увеличьте `versionCode` в `app/build.gradle.kts` и подготовьте запись в [CHANGELOG.md](../CHANGELOG.md).

```sh
./gradlew clean testDebugUnitTest testReleaseUnitTest lintDebug lintRelease assembleRelease
```

Результат: `app/build/outputs/apk/release/app-release-unsigned.apk`. Release-конфигурация использует R8, сокращение ресурсов и отключённую отладку.

Сохраните R8 mapping из `app/build/outputs/mapping/release/` вместе с внутренними материалами выпуска. Для анализа ошибки нужен mapping именно той сборки, в которой она возникла.

## Проверка на устройстве

До публикации проверьте:

- повторный подсчёт одного списка с заранее известным результатом;
- прерывание подсчёта, очистку и блокировку закрытия активной панели;
- раскрытие и сворачивание панели у краёв экрана, обе темы и увеличенный шрифт;
- сохранение, открытие и передачу XLSX, в том числе отсутствие приложения для его просмотра;
- обновление предыдущего подписанного релиза и установку с включённым Play Protect.

Зафиксируйте модель устройства, версии Android и One UI. Автотесты не проверяют взаимодействие со всеми приложениями-источниками и системными оболочками.

## Подпись

Все обновления должны использовать постоянный ключ Kerimli Systems. Приватный ключ и пароль хранятся вне репозитория и артефактов CI.

Скрипт ожидает каталог с файлами `offline-counter.p12` и `keystore.password`:

```sh
export APKSIGNER_JAR="$ANDROID_HOME/build-tools/36.0.0/lib/apksigner.jar"
bash scripts/sign-release.sh \
  app/build/outputs/apk/release/app-release-unsigned.apk \
  Offline-Counter-release.apk \
  /absolute/path/to/signing-private
```

Скрипт подписывает APK и проверяет подпись через `apksigner`. Сверьте SHA-256 сертификата с предыдущим релизом. После подписи содержимое APK изменять нельзя.

```sh
java -jar "$APKSIGNER_JAR" verify --verbose --print-certs Offline-Counter-release.apk
sha256sum Offline-Counter-release.apk
```

Debug- и release-сборки имеют разные сертификаты. При переходе с debug-сборки сначала сохраните необходимые результаты вне приложения: Android не устанавливает обновление с несовместимой подписью.

## Публикация

1. Создайте тег `v<versionName>` на проверенном коммите.
2. Подготовьте описание в `docs/releases/<versionName>.md`: изменения, требования к установке и сведения о проверке.
3. Создайте GitHub Release для этого тега.
4. Прикрепите подписанный APK, `SHA256SUMS.txt` и вывод проверки сертификата в `signature.txt`.
5. Скачайте опубликованный APK и сравните его контрольную сумму с исходным подписанным файлом.

Название APK в файле контрольных сумм должно совпадать с именем вложения. Ключи и пароли не входят в состав релиза.

Изменения текста в `docs/releases/` автоматически синхронизируются с описаниями уже существующих GitHub Releases. Этот процесс не создаёт релизы и не изменяет теги или вложения.

## Play Protect

Подпись обеспечивает совместимость обновлений, но не гарантирует отсутствие предупреждений Play Protect. При предполагаемом ложном срабатывании сохраните точный текст предупреждения и подайте [апелляцию](https://support.google.com/googleplay/android-developer/contact/protectappeals) для конкретного подписанного APK.

Справочные материалы: [подпись Android-приложений](https://developer.android.com/studio/publish/app-signing) и [Google Play Protect](https://developers.google.com/android/play-protect).
